# ShlapaBank

| Что | Адрес |
| --- | --- |
| Приложение (UI) | http://localhost:8080/ |
| Swagger (документация API) | http://localhost:8080/docs |
| Health-check | http://localhost:8080/health |

## Быстрый старт

Нужен установленный Docker Desktop.

Шаг 1 — склонировать репозиторий:

```bash
git clone <адрес-репозитория> shlapabank
cd shlapabank
```

Шаг 2 — запустить всё разом:

```bash
docker compose up --build
```

Первый запуск занимает 1–3 минуты (собирается фронт, сеются пользователи). Дальше — секунды.

Шаг 3 — открыть в браузере http://localhost:8080/ — увидите экран входа. Готово.

**Остановить:** `Ctrl+C` в терминале, потом `docker compose down`.
**Полностью сбросить (включая базу):** `docker compose down -v && docker compose up --build`.

## Учётные записи по умолчанию

**Демо-клиент** — на экране входа есть кнопка «Войти в демо-режим», которая логинит вас без ввода. У этого пользователя заранее подготовлены счета в разных валютах, несколько карт и история операций за 30 дней. Идеально, чтобы посмотреть, как всё выглядит и что тестировать. Учётка для входа через API/Swagger: логин `fullclient`, пароль `FullClient1!`, телефон `+79991234567`.

**Админ** — логин `admin`, пароль `admin`. Нужен для:

- посмотреть **всех пользователей** в системе (`GET /admin/users`);
- **заблокировать** или **разблокировать** пользователя (`POST /admin/users/{id}/block` / `unblock`);
- **удалить** любого пользователя со всеми его счетами и историей (`DELETE /admin/users/{id}`);
- настроить, в **какие внешние банки** ему разрешено переводить по СБП (`PUT /admin/users/{id}/banks`);
- посмотреть **все транзакции** пользователя (`GET /admin/users/{id}/transactions`);
- полностью **сбросить БД** к исходному состоянию (`POST /admin/restore-initial-state`) — оставляет только самого админа.
- управлять **тренажёром QA** — включать/выключать режим багов и искусственные задержки, скачивать «ключ ответов» (см. [Тренажёр QA](#тренажёр-qa-режим-багов-задержки-лог-панель)).

Дефолтного админа нельзя ни удалить, ни заблокировать. В UI **есть** админ-панель: залогинившись админом, откройте `/admin` (пункт виден только пользователю с ролью ADMIN) — там управление пользователями и тумблеры тренажёра QA. Те же операции доступны через Swagger или свой скрипт.

## Бизнес-требования

Тут для каждого модуля написано:

- **Что должно работать** — с точки зрения клиента.
- **Как это сделать через UI** — куда кликать.
- **Как это сделать через API** — какой эндпоинт дёргать.
- **Что имеет смысл тестировать** — типичные сценарии, включая ошибки.

### Регистрация и вход

**Что должно работать:**

- Пользователь может завести аккаунт: логин + пароль.
- После регистрации — сразу логин и переход в дашборд.
- Логин 6–20 символов, только латиница и цифры. Логин уникальный.
- Телефон не обязателен при регистрации — задаётся позже в профиле (без него просто нельзя принять перевод по номеру телефона, СБП).
- Пароль 8–30 символов, минимум по одной: **строчной**, **заглавной**, **цифре**, **спецсимволу** (`!@#$%^&*` и т.п.). Без пробелов. Не должен совпадать с логином.
- Вход по логину **или** по телефону — одно и то же поле, тип определяется автоматически.
- 5 неверных попыток входа подряд → пользователь блокируется. Разблокировать может только админ.
- Забыл пароль → 3 шага: ввод логина → OTP → новый пароль.

**Как в UI:**

- Открыть `/` → форма входа. Ссылка «Зарегистрироваться» ведёт на форму регистрации (логин → пароль).
- Кнопка «Забыли пароль?» открывает 3-шаговый визард восстановления.

**Как в API:**

- `POST /auth/register` — создать пользователя. Тело: `{login, password}`.
- `POST /auth/login` — войти. Тело: `{login, password}`. Возвращает `{access_token, role}`.
- `POST /auth/password/reset-request` — начать восстановление. Тело: `{login}`. Всегда `200 OK` (не палит существование логина).
- `GET /helper/otp/preview?login=<логин>` — получить актуальный OTP-код (учебный режим, в бою заменяется на SMS).
- `POST /auth/password/reset-confirm` — установить новый пароль. Тело: `{login, otp_code, new_password}`. При успехе возвращает уже новый токен.
- `GET /auth/login-available?login=<логин>` — проверить, свободен ли логин.

**Что имеет смысл тестировать:**

- Успешная регистрация → редирект на дашборд.
- Занятый логин → `login_not_unique`.
- Слабый пароль (без спецсимвола, короткий и т.п.) → `weak_password`.
- Пароль равен логину → `password_equals_login`.
- Неверные логин/пароль → `invalid_credentials`.
- 5 подряд неверных попыток → пользователь стал `BLOCKED`, повторный вход → `user_blocked`.
- Восстановление пароля с неверным OTP → `invalid_otp_code`.

### !!!Тестовое пополнение счёта!!!

В UI в левом верхнем углу на главной страницы когда мы залогинены, есть оранжевый логотип «S» в названии SlapaBank. Клик по нему открывает модалку **тестового пополнения** — можно быстро закинуть любую сумму на любой свой счёт без OTP. Нужно для тестов, чтобы не гонять полный сценарий пополнения ради данных.

API-эндпоинт для того же самого — `POST /accounts/{id}/deposit` (в отличие от `POST /accounts/{id}/topup`, тут не требуется OTP).

Для тестов есть ещё набор helper-ручек изменения баланса без OTP: `POST /helper/accounts/{id}/increase`, `/decrease`, `/zero` (увеличить / уменьшить / обнулить). `increase?purpose=salary` доступен только админу.

### Профиль

**Что должно работать:**

- Пользователь видит и меняет свои данные: имя, фамилию, email, телефон, дату рождения, цвет аватара, тему интерфейса, основной банк для СБП.
- Имя/фамилия — только буквы, **с заглавной буквы** (`Иван`, не `иван`). Проверяется и на фронте (подсказка под полем), и на бэке.
- Может загрузить **картинку аватара** (JPEG/PNG/WebP, до 5 МБ) — заменяет цветной кружок с инициалами. Можно удалить и вернуться к цвету.
- Меняет пароль (нужен старый).
- Видит свою роль (`Клиент · Обычный` / `Админ`) — пока значения ровно два, задел на будущие уровни/тарифы клиентов.
- Может **полностью удалить свой аккаунт** — вся история и счета исчезают.

**Как в UI:**

- Клик по аватару в правом верхнем углу → пункт «Профиль» → 4 вкладки: «Личные», «Безопасность» (смена пароля + удаление), «Внешний вид» (тема, цвет аватара), «СБП-банк по умолчанию».
- На вкладке «Личные» — кнопка «Загрузить фото» рядом с аватаром. Поля имени/email/телефона валидируются прямо в форме (подсказка под полем), кнопка «Сохранить» недоступна, пока есть ошибки.
- Удалить аккаунт: «Безопасность» → «Опасная зона» → ввести слово `УДАЛИТЬ` и подтвердить.

**Как в API:**

- `GET /profile` — данные текущего пользователя.
- `PUT /profile` — обновить (все поля опциональные). Смена пароля — поля `current_password` + `new_password`.
- `POST /profile/avatar` — загрузить аватар. `multipart/form-data`, поле `file` (JPEG/PNG/WebP, до 5 МБ). Отдаёт обновлённый профиль с заполненным `avatar_url`.
- `DELETE /profile/avatar` — убрать картинку, вернуться к цветному кружку.
- `DELETE /profile` — самоуничтожение, каскадно удаляет счета, карты, транзакции.

**Что имеет смысл тестировать:**

- Смена имени/фамилии → аватар в шапке обновился.
- Загрузка аватара → картинка появилась в шапке и на странице «Личные данные»; неподдерживаемый тип файла → `avatar_invalid_type`; файл больше 5 МБ → `avatar_too_large`.
- Удаление аватара → снова показывается цветной кружок с инициалами.
- Смена пароля с неверным текущим → `invalid_current_password`.
- Занятый email/телефон → `email_not_unique` / `phone_not_unique`.
- Удаление аккаунта → следующий запрос с этим токеном → `invalid_token`.

### Счета

**Что должно работать:**

- 4 валюты: RUB, USD, EUR, CNY. 2 типа: DEBIT (обычный) и SAVINGS (накопительный, с него нельзя переводить).
- Пользователь может открыть до 3 счетов в каждой валюте.
- Каждому счёту можно дать имя (иначе он называется «Счёт N» / «Накопительный N»).
- Пополнение из UI по кнопке-логотипу — быстрое, без OTP. Пополнение с подтверждением (моделирует «настоящее» пополнение) — с OTP.
- Закрыть можно только счёт с нулевым балансом.

**Как в UI:**

- Дашборд → карточка «Счета» → «Открыть счёт» → выбрать валюту и тип.
- Клик по счёту → страница деталей: там же переименование, закрытие, полный номер, пополнение.
- Быстрое пополнение: клик по оранжевому логотипу «S» в шапке → модалка (см. [Тестовое пополнение счёта](#тестовое-пополнение-счёта)).

**Как в API:**

- `GET /accounts` — свои счета.
- `GET /accounts/{id}` — детали одного.
- `POST /accounts` — открыть новый. Тело: `{currency, account_type, name?}`.
- `PATCH /accounts/{id}` — переименовать.
- `DELETE /accounts/{id}` — закрыть.
- `POST /accounts/{id}/deposit` — быстрое пополнение (без OTP, для UI-виджета).
- `POST /accounts/{id}/topup` — пополнение с OTP.

**Что имеет смысл тестировать:**

- Открыть 4-й рублёвый счёт → `account_limit_exceeded`.
- Закрыть счёт с балансом > 0 → `account_close_requires_zero_balance`.
- Пополнить чужой счёт → `forbidden_account_access` / 404.
- Пополнение отрицательной суммой → `amount_must_be_positive`.

### Карты

**Что должно работать:**

- 2 типа: **Regular** (обычная, 3 базовых дизайна — CLASSIC / EMERALD / GRAPHITE) и **Gold** (премиум, 4 золотых дизайна — SUNSET / ROSE / GOLD_BAR / GOLD_MARBLE).
- Привязывается к DEBIT-счёту. На один счёт — до 5 карт.
- Платёжная система подбирается автоматически: RUB → МИР, остальные валюты → VISA.
- Можно заблокировать/разблокировать, сменить дизайн, перевыпустить, закрыть.
- «Показать полный номер» открывает номер и CVV (в учебной версии CVV детерминированный — не меняется при перезагрузке).

**Как в UI:**

- Дашборд → раздел «Карты». Клик по карте → страница деталей.
- Кнопка «···» на карте → блокировка, смена дизайна, лимиты, перевыпуск, закрытие. Всё это в модалках.

**Как в API:**

- `GET /cards` — свои карты.
- `GET /cards/{id}` — одна карта.
- `POST /cards` — выпустить. Тело: `{account_id, card_type, design}`.
- `GET /cards/{id}/reveal` — вернёт полный номер и CVV.
- `PATCH /cards/{id}` — сменить статус (`ACTIVE`/`BLOCKED`) и/или дизайн.
- `POST /cards/{id}/reissue` — атомарный перевыпуск: старая закрывается, новая с тем же типом/дизайном, но новым номером и датой.
- `DELETE /cards/{id}` — закрыть.

**Что имеет смысл тестировать:**

- Выпустить Regular с золотым дизайном (например SUNSET) → ошибка.
- 6-я карта на один счёт → `card_limit_exceeded`.
- Заблокировать → карта не участвует в переводах, попытка перевести с неё → `card_not_active`.
- Reveal одной карты много раз → CVV одинаковый.
- Reissue → у новой карты другой номер, новый CVV.

### Переводы

**Что должно работать — 4 типа переводов:**

1. **Между своими счетами.** Без OTP. Валюты должны совпадать — при разных валютах вернётся `currency_mismatch`. Конвертация между валютами — это **отдельная** операция «Обмен валют» (`POST /transfers/exchange`, требует OTP), а не этот перевод.
2. **По номеру счёта.** Если счёт находится в ShlapaBank → внутренний перевод без комиссии. Если не находится → внешний, комиссия 5 %.
3. **По номеру телефона (СБП).** Только RUB. Если получатель — клиент ShlapaBank → без комиссии. Если внешний банк → комиссия 2 %.
4. **По номеру карты.** Внутренняя карта → без комиссии, внешняя → комиссия 1.5 %.

Все переводы, кроме «между своими», требуют OTP. Есть суточные и разовые лимиты. Со счёта типа SAVINGS переводить нельзя.

**Важно про перевод по телефону:** телефон у пользователя не обязателен (см. [Регистрация и вход](#регистрация-и-вход)) — если у получателя, даже клиента ShlapaBank, телефон не указан в профиле, найти его по номеру невозможно. Система не отличает «это правда другой банк» от «это клиент ShlapaBank без указанного телефона» — обе ситуации выглядят одинаково (телефон просто ни у кого не найден), поэтому и в UI, и в сообщении об ошибке `recipient_not_found_in_our_bank` есть напоминание попробовать перевод по номеру карты или счёта, если получатель точно клиент ShlapaBank.

**Как в UI:**

- Дашборд → кнопка «Перевести». В UI доступны плитки: по номеру телефона, по номеру карты, между своими, обмен валют. Перевод **по номеру счёта** реализован на бэкенде, но отдельной плитки в UI нет — дёргается через API.
- В каждой форме сверху показывается статус получателя (найден в нашем банке / внешний, комиссия такая-то).
- OTP-подсказка встроена в форму — можно скопировать код в один клик (учебная фича).

**Как в API:**

- `POST /transfers` — между своими (валюты должны совпадать).
- `POST /transfers/exchange` — обмен валют между своими счетами (конвертация по курсу). Требует OTP.
- `GET /transfers/rates` — текущие курсы к RUB.
- `GET /transfers/by-account/check?target_account_number=...` → узнать, наш это счёт или внешний.
- `POST /transfers/by-account` — внутренний по счёту.
- `POST /transfers/external-by-account` — внешний по счёту (комиссия 5 %).
- `GET /transfers/by-phone/check?phone=...` → узнать список банков получателя.
- `POST /transfers/by-phone` — СБП.
- `GET /transfers/by-card/check?number=...` → узнать, наша это карта.
- `POST /transfers/by-card` — по номеру карты.
- `GET /transfers/daily-usage` — остаток суточного лимита по каждой валюте.
- `GET /helper/otp/preview` — актуальный OTP для текущего пользователя.

**Что имеет смысл тестировать:**

- Перевод самому себе на тот же счёт → `transfer_same_account`.
- Разные валюты в «между своими» (`POST /transfers`) → `currency_mismatch`. Конвертация — через отдельный `POST /transfers/exchange` (обмен по курсу; `currency_not_supported_for_exchange`, если у валюты нет курса).
- Недостаточно средств → `insufficient_funds`.
- Превышение суточного лимита → `transfer_amount_exceeds_daily_limit`.
- Неверный OTP → `invalid_otp_code`.
- Свой номер карты в by-card check → в ответе `is_own: true`.
- Со счёта SAVINGS → `transfer_not_allowed_from_savings`.
- Перевод по телефону клиенту ShlapaBank без указанного телефона → ведёт себя как «получатель не в нашем банке» (`inOurBank: false` в check, `recipient_not_found_in_our_bank` при попытке отправить как внутренний).

### Платежи

**Что должно работать:**

- **Мобильная связь** — оператор + телефон + сумма (100–12 000 ₽) + OTP. Операторы учебные/пародийные: `Babline`, `MTSha`, `MegaFun`, `TelePanda`, `YotaLike` (актуальный список — `GET /payments/mobile/operators`; названия вроде «МТС»/«Мегафон» не принимаются).
- **Поставщики услуг** — 4 категории:
  - ЖКХ (вода, газ, электричество, общий ЖКХ)
  - Интернет и ТВ
  - Образование
  - Благотворительность
  Для каждого поставщика своя длина лицевого счёта. Названия поставщиков тоже учебные (`CityWater`, `GasEnergy`, `ZhKH-Service`, `RostelCom+`, `TV360`, `UniEdu`, `GoodHands` и т.д.) — полный список с длинами счетов и диапазоном сумм отдаёт `GET /payments/vendor/providers`. Сумма платежа поставщику: 100–500 000 ₽.
- Платить можно только с RUB-счёта.

**Как в UI:**

- Дашборд → «Платежи» → 2 подраздела: «Мобильная связь» и «Поставщики». В UI автоматически проверяется длина лицевого счёта и сумма.

**Как в API:**

- `GET /payments/mobile/operators` — список операторов и диапазон сумм.
- `GET /payments/vendor/providers` — список всех поставщиков с длинами счетов и диапазонами сумм.
- `POST /payments/mobile` — платёж за связь.
- `POST /payments/vendor` — платёж поставщику.

**Что имеет смысл тестировать:**

- Оплата с USD-счёта → `payment_requires_rub_account`.
- Сумма мобильной вне диапазона (например 50 ₽ или 20 000 ₽) → `payment_amount_out_of_range`.
- Неверная длина лицевого счёта → `payment_account_length_mismatch`.
- Незнакомый оператор/провайдер → `payment_operator_not_supported` / `payment_provider_not_supported`.
- Успех → в истории появляется транзакция типа `PAYMENT`.

### Инвестиции

Отдельный брокерский раздел — **умышленно перегруженный интерфейс** (терминал), сделанный специально под практику автотестов: живые котировки, дублирующиеся элементы, разные форматы одних и тех же чисел, вложенные табы, многошаговые формы. Это не «режим багов» (там togglable дефекты) — здесь всё работает корректно, просто плотно и «по-взрослому».

**Что должно работать:**

- **Брокерский счёт.** У каждого клиента есть отдельный брокерский счёт (`BRK-XXXXXX`, только RUB). В общем списке счетов он не показывается и в обычных переводах не участвует. Пополняется с обычного RUB-счёта и выводится обратно (с OTP).
- **Каталог инструментов.** 4 класса: **акции**, **облигации**, **фонды**, **валюта** (пары к рублю). Тикеры/названия учебные (`SHLP`, `PNKF`, `GZVK-BO1`, `SHMX`, `USD/RUB`…). У акций — лот (1/10/100 шт) и, у части, дивиденды; у облигаций — купон и дата погашения.
- **Живые котировки.** Цена каждого инструмента считается детерминированным симулятором рынка и **тикает каждые ~2 секунды**. С заданным `INVEST_SEED` котировки воспроизводимы (одинаковы на всех клиентах); без сида — просто плавают. Реальному рынку не соответствуют.
- **Портфель.** Позиции (тикер, количество, средняя цена), их текущая оценка и P&L (в рублях и процентах), свободный кэш, суммарная стоимость.
- **Заявки — два типа:**
  - **Рыночная (MARKET)** — исполняется сразу по текущей цене.
  - **Лимитная (LIMIT)** — висит со статусом `ACTIVE` и **исполняется лениво**, как только рынок пересечёт указанную цену (проверяется при каждом чтении портфеля/заявок). Пока висит — её можно отменить. Лимитная цена не может отстоять от рынка дальше ±20 %.
- Покупка/продажа требуют **OTP**. Комиссия брокера **0,3 %** от суммы сделки. Количество должно быть кратно лоту. Сумма сделки — 100 … 5 000 000 ₽.
- Деньги ходят через брокерский счёт; каждая сделка попадает в общую **историю операций** (тип `INVEST`) и в неё можно скачать чек. В «расходы» месяца сделки **не** попадают (это движение своих денег, а не трата).
- **Дивиденды и купоны** — календарь выплат по каталогу.
- **Экспорт заявок в CSV.**

**Как в UI:**

- Пункт меню **«Инвестиции»** → терминал `/invest`: сводка портфеля, бегущая строка котировок, список позиций, таблица котировок (табы по классам + чипы по секторам), список заявок, календарь дивидендов. Кнопки «Пополнить»/«Вывести» — модалка кэша; «Купить»/«Продать» — модалка сделки (3 шага: параметры → подтверждение → OTP).
- Клик по инструменту → карточка `/invest/instrument/{ticker}` с вкладками: **Обзор** (график + open/high/low/объём), **Стакан** (живой, перерисовывается), **Дивиденды**, **О бумаге**.

**Как в API** (тег `invest`, все ручки требуют JWT):

- `GET /invest/instruments?cls=&sector=&q=` — каталог с котировками.
- `GET /invest/quotes` — лёгкая лента котировок (для бегущей строки).
- `GET /invest/instruments/{ticker}` — карточка инструмента (сводка за день + внутридневной ряд + позиция).
- `GET /invest/instruments/{ticker}/orderbook?depth=` — стакан заявок.
- `GET /invest/portfolio` — кэш + позиции + P&L (по пути **лениво исполняет** созревшие лимитки).
- `GET /invest/orders?status=` — заявки (тоже с ленивым исполнением).
- `POST /invest/orders` — выставить заявку. Тело: `{ticker, side (BUY/SELL), order_type (MARKET/LIMIT), quantity, price?, otp_code}`.
- `DELETE /invest/orders/{id}` — отменить активную лимитку.
- `POST /invest/orders/cancel-all` — отменить все активные.
- `POST /invest/cash/deposit` / `POST /invest/cash/withdraw` — пополнение/вывод брокерского счёта. Тело: `{account_id, amount, otp_code}`.
- `GET /invest/dividends` — календарь дивидендов/купонов.
- `GET /invest/orders/export.csv` — выгрузка заявок в CSV.

**Что имеет смысл тестировать:**

- Рыночная покупка при достаточном кэше → позиция появилась/увеличилась, кэш уменьшился на `сумма + 0,3 %`, в истории операция `INVEST`.
- Покупка дороже свободного кэша → `insufficient_broker_funds`.
- Продажа большего количества, чем в портфеле → `insufficient_position`.
- Количество не кратно лоту → `lot_size_mismatch`.
- Лимитная цена дальше ±20 % от рынка → `price_out_of_band`.
- Сумма сделки вне 100 … 5 000 000 ₽ → `invest_amount_out_of_range`.
- Неверный OTP при сделке → `invalid_otp_code`.
- Лимитная заявка на покупку **ниже** рынка → создаётся `ACTIVE`; после того как цена опустится до лимита — при следующем чтении портфеля/заявок статус становится `EXECUTED`.
- Отмена активной заявки → статус `CANCELLED`; повторная отмена → `order_not_active`.
- Пополнение брокерского счёта с RUB-счёта → кэш вырос, баланс RUB-счёта уменьшился; вывод — обратно.
- Попытка перевести на/с брокерского счёта обычным переводом → `transfer_not_allowed_for_brokerage`.

**Что здесь автоматизировать (раздел сделан ровно для этого):**

Заложенные «неудобства» — это **постоянная логика**, не отключаемый режим. На них и тренируемся:

- **Дублирующиеся `data-testid`.** Кнопки «Купить»/«Продать» встречаются в позициях, в таблице котировок и в карточке инструмента — у всех одинаковые `data-testid="invest-buy-btn"` / `invest-sell-btn`. Урок: цепляться за контейнер (строку/позицию), а не за глобальный локатор.
- **Живые котировки** тикают каждые ~2 c. Проверять надо по состоянию (`wait until`), а не по фиксированному `sleep`; для стабильности прогонов — фиксировать `INVEST_SEED`.
- **Один и тот же рубль в разных форматах.** В сводке портфеля: `₽ 1 245 630,42`, `RUB 58214.90`, `209780.00 RUB`. Урок: нормализовать числа перед сравнением.
- **Вложенные табы и чипы.** Класс инструмента (акции/облигации/фонды/валюта) + сектор (банки/телеком/…) в таблице, плюс отдельные вкладки в карточке инструмента.
- **Многошаговая форма сделки.** Параметры → подтверждение → OTP; на каждом шаге свои элементы и своя валидация.
- **Стакан перерисовывается** на каждом обновлении, у строк нет стабильных id — нельзя привязываться к конкретной строке по индексу.
- **Асинхронное (ленивое) исполнение лимиток** — состояние заявки меняется «само» между запросами: отличный кейс для polling-ассертов с таймаутом.
- **Тикеры со слэшем** (`USD/RUB`) в URL карточки — проверка кодирования маршрутов.

Идеи сценариев: полный happy-path покупки с проверкой баланса и истории; проверка расчёта комиссии (сумма×0,3 %) сверкой превью и фактического списания; жизненный цикл лимитной заявки (создать ниже рынка → дождаться исполнения → проверить позицию); негативные кейсы по кодам ошибок из списка выше; сверка «Итого спишется» в модалке с фактическим изменением кэша.

### История и статистика

**Что должно работать:**

- Все операции пользователя видны в одном списке, отсортированы по дате (свежие сверху).
- Есть подгрузка «показать ещё» — пагинация **клиентская**: эндпоинт `GET /transactions` отдаёт все операции сразу, без параметров `limit`/`offset`.
- По каждой операции можно открыть модалку с деталями или скачать HTML-чек.
- В сайдбаре виджет «Инсайты» — сколько потрачено в этом месяце + топ-2 категории расходов. Это просто статистика, не привязанная ни к какому лимиту (лимита на траты в проекте нет).
- Кнопка «Подробная аналитика →» открывает модалку с полной разбивкой по категориям (донат-диаграмма + список категорий с суммами и процентами) и стрелками «‹ / ›» для переключения на предыдущий/следующий месяц (в будущее дальше текущего месяца уйти нельзя).

**Как в UI:**

- Дашборд → «История». Фильтр по типу (топап/перевод/платёж), поиск по описанию, экспорт CSV.
- Клик по любой операции → модалка с деталями.
- Ссылка «Скачать чек» → HTML-файл открывается в браузере.
- Сайдбар → «Инсайты» → «Подробная аналитика →» — модалка с разбивкой по категориям за текущий месяц.

**Как в API:**

- `GET /transactions` — все операции.
- `GET /transactions/{id}` — одна операция в JSON.
- `GET /transactions/{id}/receipt` — HTML-чек (браузер скачает файл).
- `GET /statistics/monthly?year=YYYY&month=MM` — общая сумма трат за месяц + разбивка по категориям (`{period, currency, spent, categories: [{key, label, amount}]}`).

**Что имеет смысл тестировать:**

- После платежа → операция появляется в списке.
- Скачивание чека → успешный HTTP 200, HTML корректно рендерится.
- Статистика: за месяц с операциями `spent` и `categories` заполнены, за пустой месяц — `spent: "0.00"`, `categories: []`, без ошибки.
- «Подробная аналитика →» открывает модалку с той же разбивкой, что и в сайдбаре, только полностью (не только топ-2).

## Swagger — как читать документацию API

Swagger доступен по адресу http://localhost:8080/docs — это интерактивная документация всех API.

**Как выглядит:**

- Сверху — общее описание проекта и формат ошибок.
- Дальше — эндпоинты, сгруппированные по тегам: **admin** (сверху), **auth**, **profile**, **accounts**, **cards**, **transfers**, **payments**, **transactions**, **statistics**, **helper**.
- Каждый эндпоинт можно раскрыть → увидеть параметры, пример тела, пример ответа, все возможные ошибки.
- Кнопка **Try it out** — заполнить форму и отправить запрос прямо из браузера.

### Как авторизоваться в Swagger

Все эндпоинты, кроме `/auth/register`, `/auth/login`, `/auth/login-available`, `/auth/password/*` и `/helper/otp/preview?login=…`, требуют JWT-токен.

Пошагово:

1. Раскрыть `POST /auth/login`, нажать **Try it out**.
2. В теле подставить учётку. Для админа:
   ```json
   {"login": "admin", "password": "admin"}
   ```
   Для сгенерированного клиента (пример):
   ```json
   {"login": "u12345678", "password": "U12345678A1a!"}
   ```
3. Нажать **Execute** и скопировать `access_token` из ответа.
4. Прокрутить наверх страницы Swagger, нажать зелёную кнопку **Authorize**.
5. Вставить токен (без слова `Bearer` — Swagger добавит сам) и нажать **Authorize**, потом **Close**.
6. Теперь у всех эндпоинтов замочки закрылись — можно дёргать защищённые.

### Зачем тег «admin»?

Тег наверху потому, что это отдельный набор операций для сотрудника банка (не клиента): просмотр всех пользователей, блокировка, удаление, настройка внешних банков, сброс БД. См. раздел [Учётные записи по умолчанию](#учётные-записи-по-умолчанию).

### Полезные SQL-запросы

**Все клиенты с 2+ активными счетами:**

```sql
SELECT u.login, COUNT(a.id) AS accounts_count
FROM users u
JOIN accounts a ON a.user_id = u.id AND a.is_active
GROUP BY u.id
HAVING COUNT(a.id) >= 2
ORDER BY accounts_count DESC
LIMIT 20;
```

**Топ-50 по суммарному рублёвому балансу:**

```sql
SELECT u.login, u.first_name, u.last_name, SUM(a.balance) AS total_rub
FROM users u
JOIN accounts a ON a.user_id = u.id AND a.currency = 'RUB' AND a.is_active
GROUP BY u.id
HAVING SUM(a.balance) > 0
ORDER BY total_rub DESC
LIMIT 50;
```

**Все золотые карты и их владельцы:**

```sql
SELECT u.login, c.last4, c.design, a.currency, a.balance
FROM cards c
JOIN accounts a ON a.id = c.account_id
JOIN users u ON u.id = a.user_id
WHERE c.card_type = 'GOLD' AND c.status = 'ACTIVE'
LIMIT 100;
```

**Заблокированные пользователи:**

```sql
SELECT id, login, phone, failed_login_attempts
FROM users
WHERE status = 'BLOCKED';
```

**Транзакции пользователя за 30 дней:**

```sql
SELECT t.created_at, t.type, t.amount, t.currency, t.description
FROM transactions t
WHERE t.initiated_by = (SELECT id FROM users WHERE login = 'fullclient')
  AND t.created_at >= NOW() - INTERVAL '30 days'
ORDER BY t.created_at DESC;
```

**Все транзакции с комиссиями (доход банка):**

```sql
SELECT currency, SUM(fee) AS total_fees, COUNT(*) AS operations
FROM transactions
WHERE fee > 0
GROUP BY currency;
```

**Очистить сгенерированных пользователей (кроме демо и админа):**

```sql
DELETE FROM users
WHERE login NOT IN ('fullclient', 'admin')
  AND login LIKE 'u%';
```

## Дополнительно

### Единый формат ошибок

Любая 4xx/5xx-ошибка возвращается в одном формате:

```json
{
  "error": {
    "code": "insufficient_funds",
    "message": "Недостаточно средств",
    "field": null
  }
}
```

- **`code`** — стабильный snake_case-идентификатор. Не меняется, безопасно использовать в автотестах и логике фронта.
- **`message`** — русский текст, готовый к показу пользователю. Для ошибок из бизнес-логики (`raise HTTPException(...)`) — берётся из словаря `error_messages.py`. Для ошибок валидации полей Pydantic (`RequestValidationError`) — тоже человекочитаемый, а не сырой технический текст библиотеки (`"String should match pattern..."` и т.п. никогда не долетают до клиента).
- **`field`** — имя поля-виновника для валидационных ошибок (например `field: "password"`). Для бизнес-ошибок `null`.

Полный список всех кодов и сообщений — в файле `backend/app/error_messages.py`.

### Единая ручка OTP

`GET /helper/otp/preview` — **единственная точка** получения OTP для всех операций (переводы, платежи, смена пароля, восстановление).

Два режима:

- **С Bearer-токеном (без параметров)** → вернёт код для текущего пользователя. Так работают все операции внутри UI после логина.
- **Без токена, с `?login=<логин>`** → вернёт код для указанного логина. Так работает экран «Забыли пароль?».

В учебном режиме код всегда возвращается прямо в JSON — не нужно ловить SMS. В проде эта ручка закрывается.

### Массовый сид пользователей

При запуске бэкенда, если пользователей в БД меньше `BULK_SEED_USERS` (по умолчанию 50 000), автоматически досеиваются недостающие. Каждый — с рандомным именем, 1–4 счетами, 0–3 картами и 0–15 операциями за 90 дней. Пароль вычисляется по формуле из раздела [Учётные записи по умолчанию](#учётные-записи-по-умолчанию).

**Управление** через переменные окружения (в `docker-compose.yml`):

- `BULK_SEED_ENABLED=1` — включить (по умолчанию), `0` — выключить.
- `BULK_SEED_USERS=50000` — сколько всего пользователей должно быть.

Первый запуск с сеятелем — 30–90 секунд (батчи по 1000). Дальше сеятель видит, что цель достигнута, и не делает ничего.

> Примечание: в самом приложении массовый сид по умолчанию **выключен** (`BULK_SEED_ENABLED=0`), но в `docker-compose.yml` он принудительно включён (`BULK_SEED_ENABLED=1`), поэтому при запуске через Docker пользователи сеются.

### Тренажёр QA: режим багов, задержки, лог-панель

Стенд умеет специально «портиться» — это учебный тренажёр для отработки поиска дефектов и написания устойчивых автотестов. Управление — тумблерами в UI (`/admin`, только для админа) или через env / admin-API.

**1. Режим багов («найди баг»).**

Выключен по умолчанию (`ENABLE_BUGS=false`). Когда **выключен** — приложение работает корректно, ровно как описано в бизнес-требованиях выше. Когда **включён** — активируется набор из 10 намеренных дефектов на всех слоях (в админской учетке в авдин панеле можно скачать список с описанием багов)

**2. Искусственные задержки (chaos).**

**Включены по умолчанию** (`ENABLE_CHAOS=true`) — сервер отвечает не мгновенно, а с рандомным лагом: базовые 120–450 мс, +300–900 мс на «тяжёлых» ручках (переводы, выпуск карты, статистика, проверки), и изредка «толстый хвост» до ~4 с. Ошибок при этом не вносится — только задержки, чтобы автотесты ждали состояние UI, а не фиксированный `sleep`.

- `GET /admin/chaos` / `PUT /admin/chaos` (`{enabled}`) — статус и тумблер.
- env: `ENABLE_CHAOS=false` — выключить; `CHAOS_SEED=<строка>` — воспроизводимый «рандом»; `CHAOS_*_MS` — настройка профиля задержек.
- Заголовок `X-SB-No-Chaos: 1` в запросе — обойти задержку для служебных проверок.

**3. Флаги стенда и лог-панель.**

- `GET /api/v1/flags` — без авторизации возвращает `{bugs_enabled, chaos_enabled, dev_trace_enabled}`. Фронт читает их, чтобы включать клиентские баги и знать режим стенда.
- На всех страницах UI живёт лог-панель (dev-trace): метод, путь, статус и длительность запросов. Управляется `ENABLE_DEV_TRACE` (по умолчанию включено вне production).
