# Демо-клиент `fullclient` — правила поддержки

## Что это

`fullclient` — встроенный тестовый пользователь, у которого при первом запуске проекта автоматически создаются: счета в разных валютах, карты разных дизайнов и типов, богатая история операций по всем категориям.

Логин: **`fullclient`**  
Пароль: **`FullClient1!`**  
Телефон: **`+79991234567`**  

Логика сидирования — в `backend/app/startup.py`, функция `_seed_full_client`.

## Главное правило

**Любое изменение функциональности проекта ДОЛЖНО сопровождаться апдейтом сидера `fullclient`.**

Смысл в том, что демо-клиент — это витрина: тестировщик логинится и сразу видит всё, что умеет банк. Если добавили фичу — она должна быть представлена в демо-данных; если убрали — соответствующие данные тоже надо убрать, чтобы не мозолили глаза.

## Что именно поддерживать

Каждый раз при изменении смотреть на список ниже и синхронизировать:

1. **Новая сущность (модель + миграция)** → добавить хотя бы один экземпляр в сидер.
   Пример: добавили `Card` → сидер выпускает по карте к каждому дебетовому счёту.

2. **Новый тип / новая категория / новый enum-value** → создать хотя бы одну запись с этим значением.
   Пример: добавили дизайн `ROSE` → у одной из карт `fullclient` дизайн `ROSE`.

3. **Новая категория операций** → добавить хотя бы одну транзакцию этой категории в историю за последние 30 дней (чтобы попадала в статистику).

4. **Удалили фичу** → убрать соответствующие сидовые данные и, при необходимости, миграцию-очистку.

5. **Поменяли схему поля** (обязательное → опциональное, новый required-параметр и т.п.) → обновить вызовы в сидере.

## Как обновлять

Сидер **идемпотентный**: при каждом старте проверяет, есть ли уже нужные данные, и создаёт только недостающее. Это значит:

- **Добавление** новых сидов работает сразу после `docker compose up --build` — новые записи появятся у существующего `fullclient` без необходимости пересоздавать пользователя.
- **Удаление / изменение** существующих сидов может потребовать сброса БД (`docker compose down -v && docker compose up --build`), если старые записи не будут перезаписаны логикой сидера. При масштабных изменениях лучше добавить в `init_db` явный cleanup.

## Что уже сидируется (актуально на сегодня)

- **Пользователь** `fullclient` с телефоном.
- **Внешние банки** для переводов (3–5 случайных).
- **Счета:** 2 дебетовых RUB, 1 накопительный RUB, 1 дебетовый USD, 1 дебетовый EUR, 1 дебетовый CNY.
- **Карты:** к каждому дебетовому счёту — как минимум одна карта (MIR для RUB, VISA для остальных), плюс дополнительная виртуальная карта у одного из RUB-счетов, разные дизайны (CLASSIC / EMERALD / SUNSET / ROSE) распределены между картами. Одна карта — заблокирована для демо.
- **История операций** за последние 30 дней: платежи ЖКХ, мобильной связи, интернета, образования, благотворительности, переводы (внешний + p2p), пополнения. Всё в достаточном объёме, чтобы виджет «Лимит на месяц» показывал заполненный пирог.

## Что не сидируется (клиентские состояния)

- **Промо-плитки на дашборде** — статический список в `ui/src/features/promo/PromoCarousel.tsx`. Если добавляете новую фичу в продукт — обновляйте этот список: одна новая плитка = свежая витрина.
